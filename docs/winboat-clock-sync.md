# WinBoat guest clock diagnostics and synchronization

Mendimaru's Linux environment diagnostics include a **Guest clock** check that
measures the difference between the Windows guest clock and the Linux host
clock. A large skew can break Studio Pro license and certificate validation,
expire otherwise valid session tokens, and make cross-boundary log timelines
hard to interpret.

## How the skew is measured

The WinBoat Guest Server is implemented with Go's `net/http` stack. Every
response therefore carries a `Date` header generated from the Windows guest
system clock. Mendimaru samples that clock without any guest-side changes:

```text
t0   = Linux host UTC time immediately before GET /health
Date = HTTP Date header generated by the Windows guest (1-second resolution)
t1   = Linux host UTC time immediately after response headers arrive
skew = Date - (t0 + (t1 - t0) / 2)
```

The midpoint bounds the measurement error by half of the request latency plus
the one-second HTTP date resolution. On local loopback forwarding this stays
within a few seconds, while the roughly ten-hour drift reported in
issue #76 remains unmistakable.

The check reports:

| Result  | Condition                                                                   | Meaning                                              |
| ------- | --------------------------------------------------------------------------- | ---------------------------------------------------- |
| Passed  | absolute skew ≤ 5 seconds                                                   | Normal for HTTP date resolution and loopback latency |
| Warning | 5 seconds < absolute skew ≤ 60 seconds, or the header could not be measured | Investigate guest time synchronization               |
| Failed  | absolute skew > 60 seconds                                                  | Stable error code `guest-clock-skew-exceeded`        |

The observed value also includes the Linux host clock source when it can be
read safely, for example `skew=-36000s; host-clocksource=hpet`. A large
negative skew means the Windows guest clock is behind the Linux host.

The diagnostic report export keeps the existing allowlist and does not include
observed values, credentials, or configuration paths.

## Host clock source

WinBoat's container logs have reported:

```text
unsupported clock source detected: 'hpet'. Please set host clock source to 'tsc'.
```

Check the current source:

```bash
cat /sys/devices/system/clocksource/clocksource0/current_clocksource
cat /sys/devices/system/clocksource/clocksource0/available_clocksource
```

Prefer `tsc` on bare-metal Intel/AMD hosts:

```bash
# Inspect the current kernel command line
cat /proc/cmdline
```

Add `clocksource=tsc` to the kernel command line through your boot loader (for
example `/etc/kernel/cmdline` with `sbctl` or the distribution's GRUB
configuration), then reboot and verify:

```bash
cat /sys/devices/system/clocksource/clocksource0/current_clocksource
```

Do not force `tsc` on a host where it is not stable. On virtual machines,
`kvm-clock` or the hypervisor-provided source can be the correct choice.
Confirming the causal relationship between `hpet` and guest drift requires a
controlled A/B reproduction on the same VM; the diagnostic provides the
measurement, not that conclusion.

## QEMU RTC options

WinBoat launches QEMU internally. When QEMU is configured directly, prefer:

```text
-rtc base=localtime,clock=host,driftfix=slew
```

- `clock=host` keeps the RTC aligned with the host monotonic progression.
- `driftfix=slew` slews guest time instead of jumping when interrupts are
  delayed.
- Keep changes coordinated with WinBoat's managed configuration so container
  recreation does not discard them.

## Windows guest time synchronization

Inside the Windows guest, resynchronize explicitly after fixing the host:

```powershell
w32tm /resync /force
w32tm /query /status
```

Keep the Windows Time service enabled so the guest re-converges after
sleep or pause:

```powershell
Get-Service W32Time | Set-Service -StartupType Automatic
Start-Service W32Time
```

Mendimaru never writes the guest clock itself and never rewrites Studio
timestamps. Session timestamps remain guest-reported values; the Guest clock
diagnostic explains how to interpret them.
